# 告警处置手册

本手册提供共用起点；每个规则annotation.action给出具体入口。上线前补齐实际责任人、系统重要性、看板和升级联系人，不能用“运维处理”替代职责。处理顺序为：确认对象与作用域 → 检查证据和影响 → 查近期变更 → 执行已批准的恢复操作 → 验证业务与监控 → 留下复盘与阈值调整证据。

## common

抓取失败先看Targets的lastError、最后成功时间、scrape_duration和采集器日志，区分服务不可用、监控网络、鉴权、超时及重标签错误。用独立探测或业务请求确认影响。`up=1`只说明抓取成功，不保证指标完整；输入消失也不能视为恢复。修复后确认连续抓取、必需指标和告警状态均符合预期。

## linux

CPU先区分用户计算、iowait、steal和每核负载；结合进程、队列与应用延迟。内存用MemAvailable，不把缓存全部当成不可用；结合Swap活动、PSI和major faults。OOM按事件查内核日志，确认被终止进程、容器及业务影响，不能仅靠告警解除宣告恢复。

磁盘按mountpoint、device核对`df`、inode、只读状态和增长速度。空间不足先识别日志、临时文件和业务数据，按预案清理/扩容；不得未经确认删除数据库文件。IO延迟先确认IOPS样本与物理/虚拟设备层次，busy高不一定饱和。网络错误先按接口与方向定位；TCP比例同时看分子、分母、同时间窗口、端点及业务延迟，再查链路、拥塞和重传原因。主机全局统计不能直接指定某个应用连接。

系统限额先核对fd、conntrack的实际最大值和增长来源；直接提高上限可能掩盖连接泄漏。时间偏差核查NTP/chrony与虚拟化时间源。硬件RAID和SMART不由软件mdadm指标自动覆盖。

## windows

核对当前windows_exporter版本、collector权限和指标名称；旧wmi_*不能直接套用。CPU用性能分析定位进程；内存看available、committed和分页；磁盘核对真实卷、保留分区及文件增长。服务只监控明确受管清单，结合事件日志、服务依赖及端点验证。停止的计划任务、触发启动服务和禁用服务不能一律按故障处理。

## probes

确定失败发生于Exporter抓取、DNS、建连、TLS、HTTP状态还是正文匹配；从不同网络位置复核。探测点故障可能造成多目标同时失败，应确认父故障后有限抑制，不把所有端点静默。

证书检查对照线上握手的完整链、SAN、SNI、有效期及更新部署。监测到文件证书更新不证明入口已更新。到期天数是运维窗口；超过某个剩余天数的观察项不能认定违法或证书无效。确认换证后重新握手、业务访问及探测指标均已更新。

## platform

Prometheus配置失败先判断新配置未生效而旧配置仍运行，检查reload日志。规则错误按group定位表达式、匹配基数和依赖输入；漏评估检查评价耗时、查询负载和间隔。remote_write检查队列最高输入/已发送时间、失败原因和存储响应，不能仅因短期重试失败宣称数据永久丢失。

Alertmanager检查路由命中、抑制、静默和分组定时器。缺失scope标签必须先补齐，再启用精确抑制。两条不同condition、不同mountpoint或不同独立评价器的事件不能仅按同IP合并。HA分区可能重复，先区分重试、不同fingerprint、路由continue、接收器重复和网关再次发送。

VictoriaMetrics检查磁盘只读余量、写入拒绝reason和查询排队。vmalert检查datasource查询错误、延迟、输入覆盖、远程读写状态恢复；不套用Prometheus本地同组记录规则顺序的假设。未部署vmalert时不启用其规则。

## network

SNMP先核对设备、模块、权限、索引映射和ifAdminStatus/ifOperStatus，使用ifAlias确认业务接口。管理启用但物理未连可能是空口，按端口职责豁免。带宽计算注意octet→bit及ifHighSpeed的Mbit/s单位；超过标称速率或计数器重置需检查源数据。防火墙会话、丢弃原因和CPU依赖厂商MIB，不能用IF-MIB冒充完整防火墙健康。

## database

先区分Exporter可抓取与数据库可连接。核对当前实例角色、主从/集群、认证和采集权限。连接高排查连接池、长事务和泄漏；死锁/回滚先核实SQL及业务失败。复制延迟不能只看一个数字，核对线程、WAL/binlog、复制槽、通道、数据新鲜度和空闲复制语义。

Redis容量以显式maxmemory为准，0表示无限制，不能直接除0；淘汰是否有害取决于缓存/存储用途及策略。ES Red与Yellow分别核对主分片与副本分片；单节点/测试副本策略需明确。多Exporter抓同集群会重复，需要按实际cluster身份及可用性设计去重。

## messaging

RabbitMQ队列指标确认逐对象端点及vhost/queue；先看消息最老年龄、生产消费速率、消费者和资源水位，数量阈值按消息大小和时限校准。死信/延迟队列无消费者可能是设计行为。Kafka区分离线分区、ISR不足、UnderMinISR和消费者处理延迟，核查Controller模式、Broker、磁盘和复制网络。不能为消除告警盲目降低acks或min.insync.replicas。

## containers

核对容器身份、宿主机、内存limit是否有效及cgroup版本。OOM、重启和高工作集是不同事实；短生命周期容器可在抓取间隔之间消失，需要运行平台事件补充。CPU节流周期占比不等于CPU使用率或时间损失；结合实际延迟、配额和并发决定调整。

## kubernetes

以cluster/namespace/workload/pod/container定位事件，查看调度、探针、镜像、previous日志和控制器发布。OOMKilled是最后终止原因，联合重启增量后仍需确认具体事件；旧原因不能无限当成新OOM。KSM HA采集需先去重，不同集群的namespace/pod可能重名。PVC Pending检查StorageClass、配额和供应器；卷空间不足确认扩容支持、应用写入和可用字节。此模块不是完整Kubernetes控制面/etcd治理，控制面职责应引入并定制kubernetes-mixin。

## application

JVM检查GC类型、内存池、最大值是否可用及GC暂停；不能把Micrometer指标直接当作JMX Exporter名称。线程高需线程池基线与线程转储，禁止只靠扩大线程数恢复。

任务、备份及网关先确认[指标契约](CONTRACTS.md)适配确实存在且数据新鲜。RPO超限需判断最后有效恢复点，补做备份不能自动证明可恢复；恢复演练需实际验证。任务时限依业务日历，队列年龄依最老待办，不把offset当秒。网关HTTP接收、内部入队、下游发送和最终确认必须分层核对；丢失/死信须有补偿证据。

## slo

先确认SLI事件定义、分母完整性、服务级SLO及统计周期；错误预算多窗口同时满足才触发。低流量门槛可能掩盖关键失败，结合合成探测与事件严重性。检查失败请求、近期发布和依赖，依故障响应流程恢复。窗口消耗率下降不代表既有业务损失已消除。新装/断采后的长窗口不完整也会影响判断。

## watchdog

持续发送至独立deadman接收器，由外部系统在心跳缺失时通知独立渠道。按“Prometheus→Alertmanager→网关→外部心跳接收”选择实际覆盖范围；只测Alertmanager HTTP成功无法覆盖下游投递。演练停掉一个环节并确认独立通知，不能把同一条失效链路当作自己的故障通知通道。
